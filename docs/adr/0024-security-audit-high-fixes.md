# ADR-0024: セキュリティ監査（High）の対応

## メタ情報

- **ステータス**: 提案中(Proposed)
- **日付**: 2026-11-10
- **決定者**: Claude Code（承認: 人間レビュアー）

## コンテキスト（背景と課題）

takumi の `audit-security`（STRIDE + OWASP）で監査した結果、High が8件見つかった。「環境変数が未設定のとき、既定値で動く」ことと、「画面では隠しても API を直接呼ぶと通る」ことが主な原因だった。

## 決定内容

1. **未設定のときは、既定値で動かさず、拒否する（fail-closed）。**
   - Basic認証（`BASIC_AUTH_USER` / `BASIC_AUTH_PASSWORD`）: 既定値を廃止。本番で未設定なら、全リクエストを 503 で拒否する。比較は定数時間（`~/lib/safe-equal`）。
   - cron（`CRON_SECRET`）: User-Agent だけでは通さない。未設定なら全拒否。Bearer の比較も定数時間。
2. **権限の抜けを塞ぐ。**
   - 発注の支払実績（支払状況・支払日・支払元口座・支払備考）の更新は、管理者・経理だけ。
   - 案件の削除は、確定済み・請求書発行済み・支払済みの発注がある案件を拒否する。支払済みの発注の削除も拒否する。
   - 契約書・請書・請求書のPDF、工事計画のCSVは、税理士・社労士に出さない。月次レポートのPDFは、レポーティングを見られるロールだけ。
3. **メール添付とPDFのアップロードを検証する（Medium の M6・M8 を含む）。** PDF だけを受け付け、先頭の `%PDF-` とサイズ（base64で約3MB）を確認する。メール添付のファイル名から、パス・引用符・改行を除く。
4. **依存関係を更新する。** `nodemailer` を 10.4.0 に、`zod` を 4.6.7 に。
5. **Medium の追加対応。**
   - M10: 支払済みの発注は削除できない。
   - M11: 発注・案件の更新で、楽観ロックの `version` を必須にする。排他制御のある画面（支払い予定表・売上管理表）の専用の更新API（`payments.*`、`recurringPayments.*`、`receipts.misc.*`、`recurringReceipts.*`）は、その画面の scope ヘッダが無い・違う呼び出しを拒否する（受注一覧など、複数の画面から呼ばれる更新は、ADR-0017 のとおり対象外）。画面側は、子コンポーネントの処理より先に scope を設定する（`useLayoutEffect`）。
   - M12: 顧客・発注先のウェブサイトは、http(s) の URL にそろえる（スキームが無ければ https:// を付ける）。`javascript:` などは拒否し、画面のリンクも http(s) だけにする。
   - M14: 工事外の支払い・売上の更新で、金額・期日・ステータス・相手先などの変更前後を、履歴に残す。案件の予定売上の変更も残す（発注・案件・定期支払い・定期売上・振込手数料ルールの金額変更は、もともと残っている）。
   - M15: 本番のDB接続は、接続文字列に `sslmode` の指定が無ければ、通信を暗号化する（`ssl: "require"`）。

## 影響

- **デプロイ前に、本番の環境変数を設定する必要がある:** `BASIC_AUTH_USER`、`BASIC_AUTH_PASSWORD`、`CRON_SECRET`。設定せずにデプロイすると、本番に入れなくなり、cron が動かない。
- 一般社員が、API を直接呼んで支払実績を変える操作は、できなくなる（画面からの操作は、もともと経理以上だけ）。
