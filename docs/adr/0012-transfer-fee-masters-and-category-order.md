# ADR-0012: 自社口座・振込手数料マスタ、手数料の自動算出、支払い種別のドラッグ並び替え

## メタ情報

- **ステータス**: 提案中(Proposed)
- **日付**: 2026-10-13
- **決定者**: Claude Code (承認: レビュアー・保守担当)

## コンテキスト（背景と課題）

支払管理では振込手数料を支払ごとに手入力しており、入力ミスと手間が生じている。手数料は「支払元の自社口座」「振込先が同一銀行か他行か」「金額帯」で決まるため、マスタ化して自動で反映したい。あわせて、次の要件がある。

- 自社の支払元口座は最大10口座（当初は5口座。2026-10-15に変更）で、支払管理では選択枠として使う。
- 支払い種別（支払カテゴリ）の並び順をドラッグで変更でき、賞与・税金などの種別も使えるようにしたい。

共有DB（本番）のスキーマ変更を伴うため、Hard Rule 1 に従い本ADRで記録する。ADR-0006、ADR-0007 と同様、決定済みの仕様変更をまとめて扱う。

## 検討した選択肢

### 選択肢A: 手数料を従来どおり手入力のままにする

- 長所:
  - 変更が不要
- 短所:
  - 入力ミス・入力漏れが残る

### 選択肢B: 手数料ルールを設定ファイルに固定する

- 長所:
  - DB変更が不要
- 短所:
  - 銀行側の改定のたびにデプロイが必要。口座ごとの差を扱えない

### 選択肢C: 自社口座とルールをマスタ（DB）化し、サーバーが算出して行に保存する

- 長所:
  - 管理者が画面から改定できる。算出結果は行に残るため過去の支払が変わらない
- 短所:
  - テーブル2つと列2つの追加が必要

## 決定内容

選択肢Cを採用する。

- 新テーブル `company_accounts`（自社口座。論理削除、有効な表示名は一意、最大10件）と `transfer_fee_rules`（自社口座 x 宛先区分 same/other x 金額帯 [from, to) x 手数料）を追加する。
- `misc_payments` と `recurring_payments` に `company_account_id`（NULL可）を追加する。既存の `transfer_fee` 列は残し、サーバーが算出したスナップショット値として使う。
- 手数料の算出は純粋関数 `calcTransferFee`（`src/lib/transfer-fee.ts`）で行う。金額が `amount_from` 以上かつ `amount_to` 未満（上限なしは NULL）のルールの手数料を返し、該当なしは NULL。宛先区分は自社口座の銀行名と振込先銀行名を NFKC・空白除去・小文字化して比較し、一致すれば same、それ以外は other とする。
- 振込先銀行は、行の相手先と会社名が一致する発注先（論理削除除く）の銀行名とし、見つからなければ不明として other とする。
- 手数料はクライアントから受け取らない。`payments.misc.create/update` と `recurringPayments.create/update` の入力から `transferFee` を削除し、任意の `companyAccountId` を受け付ける。
- 手数料ルールや自社口座を変更しても、既存の行の `transfer_fee` は書き換えない。未払いの行は次回の編集・月次生成・支払済み切替で再算出され、まとめて反映する場合は `payments.misc.recalcFees`（未払いの案件外支払のみ）を使う。支払済みの行は口座・金額・相手先が変わらない限り保たれる。
- 支払い種別は既存の `payment_categories."order"` 列でドラッグ並び替えを行う（`paymentCategories.reorder`、管理者のみ）。新規登録は末尾に追加する。初期データに賞与・税金を追加する（冪等、手動実行）。
- 自社口座の口座番号は一覧で下4桁のみ返し、全桁は管理者専用の `getForEdit` だけが返す。履歴は `company_accounts`・`transfer_fee_rules` とも管理者のみ閲覧可とする。

## 決定の理由

手数料は口座と金額で機械的に決まるため、マスタとサーバー算出にすれば手入力の誤りを防げる。結果を行に保存することで、ルール改定後も過去の支払・集計が変わらない。口座番号の扱いは発注先マスタ（一覧は下4桁のみ）と揃えた。

## 影響

### ポジティブ

- 振込手数料の入力が不要になり、算出根拠が一貫する。
- 自社口座を選択枠として使え、並び替えも画面で完結する。

### ネガティブ

- 振込先銀行の判定は発注先マスタの銀行名の表記に依存する。発注先が未登録・銀行名が空の場合は他行宛として扱う。
- 手数料ルールの改定が既存の未払い行へ反映されるのは次回の編集・生成・`recalcFees` 実行時になる。

### フォローアップタスク
