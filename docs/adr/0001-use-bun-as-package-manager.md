# ADR-0001: Bunをパッケージマネージャ/ランタイムに採用

## メタ情報

- **ステータス**: 承認(Accepted)
- **日付**: 2026-07-03
- **決定者**: テンプレートメンテナー

## コンテキスト（背景と課題）

本リポジトリは社内の複数チームが共有するNext.js/T3 Stackベースのテンプレートである。各チームが同じ手順で依存関係をインストールし、スクリプトを実行できるよう、パッケージマネージャ兼スクリプトランナーを1つに統一する必要がある。

要件は以下のとおり。

- 依存インストールが高速で、CI・ローカルの双方でストレスが少ないこと
- スクリプト実行（`dev` / `build` / `test` など）の手順がツール横断で一貫していること
- `postinstall` によるGitフック（lefthook）の自動セットアップが確実に動くこと
- ドキュメント（CLAUDE.md / README）やAIエージェントの指示と齟齬が出ないこと

## 検討した選択肢

### 選択肢A: npm

- 長所:
  - Node.js同梱で追加インストール不要、最も広く使われている
  - エコシステムとの互換性が最も高い
- 短所:
  - インストール速度が相対的に遅い
  - ランタイムやテストランナーは別途用意する必要がある

### 選択肢B: yarn / pnpm

- 長所:
  - npmより高速で、pnpmはディスク効率にも優れる
  - ワークスペース機能が成熟している
- 短所:
  - 別途インストールとバージョン管理（Corepack等）が必要
  - ランタイムは依然Node.jsで、実行環境の統一には寄与しない

### 選択肢C: Bun

- 長所:
  - 依存インストールが非常に高速
  - パッケージマネージャ・ランタイム・スクリプトランナーを1ツールで兼ねられ、実行環境が統一される
  - `bunx` により追加のCLI（shadcn等）をワンショットで実行できる
- 短所:
  - npm/yarnに比べエコシステムが新しく、ごく一部のツールで互換性の考慮が要る場合がある

## 決定内容

パッケージマネージャ兼ランタイム兼スクリプトランナーとして **Bun** を採用する。依存関係のロックには `bun.lock` を用い、各種スクリプトは `bun run <script>`、CLIのワンショット実行は `bunx` で統一する。

## 決定の理由

複数チームが共有するテンプレートにおいて、インストール速度と「実行環境の一貫性」を最優先した。Bunはパッケージ管理・ランタイム・スクリプト実行を単一ツールで賄えるため、チームやAIツールをまたいでも手順がぶれない。エコシステムの新しさという短所は、本テンプレートが利用するライブラリ群では実害が確認されず、許容範囲と判断した。

`package.json` の `postinstall` スクリプトは、CI以外の環境で `lefthook install` を実行してGitフックを自動セットアップする。これにより `bun install` を一度実行するだけで、pre-commitフック（後述のUltraciteフォーマットとTypeScript型チェック）まで含めた開発環境が整う。

```json
"postinstall": "node -e \"if (!process.env.CI) require('child_process').execSync('lefthook install', {stdio: 'inherit'})\""
```

## 影響

### ポジティブ

- `bun install` 一発で依存インストールとGitフックのセットアップが完了する
- CI・ローカルの依存インストールが高速化する
- スクリプト実行手順（`bun run dev` など）がツール横断で統一される

### ネガティブ

- 開発者は各自の環境にBunをインストールする必要がある
- Bun固有の挙動に依存する箇所が生まれ、他ランタイムへの移行時にコストが発生しうる

### フォローアップタスク

- [x] `package.json` の `postinstall` に lefthook 自動インストールを設定
- [ ] README / セットアップスクリプトにBunのインストール手順を明記し続ける
