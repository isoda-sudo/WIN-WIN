# ADR-0007: 支払管理の定期支払い・カテゴリマスタ・支払No、および残金の廃止

## メタ情報

- **ステータス**: 提案中(Proposed)
- **日付**: 2026-10-08
- **決定者**: Claude Code (承認: レビュアー・保守担当。未決事項は末尾の「人の判断（保留中）」表を参照)

## コンテキスト（背景と課題）

ブランチ `fordevelop_0930` の支払管理に、次の要件をまとめて入れる。

- 賃料・給与・融資返済などの定期支払いを、毎月・毎年の定義から月別に展開して管理したい。
- 案件外支払のカテゴリを自由入力ではなくマスタ化したい。
- 案件に紐付かない支払にも支払Noを付けたい（発注明細側にも支払Noを持たせる）。
- 部分払い（残金）の運用をやめ、「支払済みなら確定額、それ以外は0」を実支払額とする。

共有DB（本番）のスキーマ変更を伴うため、Hard Rule 1 に従い本ADRで記録する。ADR-0006 と同様、決定済みの仕様変更をまとめて扱う。

## 検討した選択肢

### 選択肢A: 定期支払いを月ごとに先行生成して misc_payments に挿入する

- 長所:
  - 画面は misc_payments だけを見ればよい
- 短所:
  - 定義変更のたびに未来分の再生成・差分管理が必要。定期ジョブが要る

### 選択肢B: 定義だけを保持し、月別は計算で展開し、支払済みにした時点で misc_payments に具体化する

- 長所:
  - 定義変更が即座に未来月へ反映される。ジョブ不要
  - 支払の実績だけが案件外支払（10年保存対象）に残る
- 短所:
  - 月別ビューは「計算した予定」と「具体化済みの行」の合成になる

### 選択肢C: カテゴリを文字列のまま自由入力にする

- 長所:
  - スキーマ変更なし
- 短所:
  - 表記ゆれで集計できない

## 決定内容

選択肢Bを採用し、カテゴリはマスタ化する。スキーマ変更は以下のとおり。

| 対象 | 変更 |
| --- | --- |
| `payment_categories` | 新設（`id`, `name` 一意・必須, `order`, `note`, `deleted_at`, `created_at`, `updated_at`）。論理削除のみ |
| `recurring_payments` | 新設（`name`, `category_name`, `payee`, `branch`, `amount` >= 0, `frequency` monthly/yearly, `due_day` 1-31, `due_day_is_month_end`, `month_of_year` 1-12, `start_month`, `end_month`, `notes`, `version`, `deleted_at` ほか）。CHECK制約あり |
| `misc_payments` | `recurring_id`, `period`(YYYY-MM), `payment_no` を追加。`(recurring_id, period)`（recurring_id が非nullの行）と `payment_no`（非nullの行）に部分ユニークインデックス |
| `orders` | `payment_no` を追加（別担当の変更。発注明細の支払No） |
| `invoices` | `items` を追加（別担当の変更。請求書の明細を発行時に保存） |

その他の決定:

- **残金・支払履歴の削除**: 残金・支払履歴の概念を削除した（下記「Removals」参照）。実支払額は「支払済み=確定額（`orders.decided`）、それ以外=0」（`src/lib/actual-paid.ts`）。全銀CSVは画面側（`payment/page.tsx`）が `items[].amount` を組み立てて `/api/export/transfer-csv` に渡すため、金額の元は確定額である。
- **手動ステータスの制限**: 部分払いは廃止（発注明細の支払状況は 未払い / 支払済み の運用）。案件外支払の `status` は既存どおり文字列だが、定期支払いは 未払い / 支払済み のみを設定する。定期の「予定」は具体化前の表示上の状態で、DBには保存しない。
- **支払No（案件外）**: `WW{期2桁}-000-{NNN}`。期は会計期（3月決算、`fiscal-period.ts`）。NNN は同じ接頭辞の末尾連番の最大値+1。採番は `pg_advisory_xact_lock`（接頭辞キー）を取ったトランザクション内で行う。通常の案件外支払は作成時点（JST）の期、定期支払いは対象月の期を使う。
- **カテゴリ検証**: 案件外支払の作成はマスタに存在する有効なカテゴリ名のみ受け付ける。更新は据え置きなら旧値（マスタ未登録の過去カテゴリ）も許容し、変更するときだけマスタ検証する。
- **営業日繰上げは適用しない**: 支払管理は任意のカレンダー日を受け付ける仕様（D-13）で、既存の案件外支払も日付をずらさないため、定期の支払予定日も休日で前倒ししない（`payment-term.ts` の営業日処理は工事の支払期日用）。
- **権限**: 定期支払い・カテゴリ参照・案件外支払は `accountingOrAdminProcedure`、カテゴリの作成・更新・削除は `adminProcedure`。履歴は `payment_categories` を admin のみ、`recurring_payments` を admin と accounting が閲覧できる。
- **スキーマの適用**: 本リポジトリはDB変更コマンド（`db push` / `migrate`）を実行しない。保守担当が共有DBへスキーマを適用し、その後に `scripts/seed-payment-categories.ts`（冪等）でカテゴリの初期値（賃料（本社）、賃料（東京支店）、給与、融資返済、社会保険料、通信料、電気代）を投入する。適用前に本ブランチをデプロイすると該当テーブル・列が無く支払管理がエラーになる。

## 決定の理由

定義＋遅延具体化により、定義変更が未来月へ即時に反映され、定期ジョブも不要になる。実績だけを案件外支払に残すため、10年保存の対象も明確になる。カテゴリのマスタ化で集計の表記ゆれを防ぐ。残金は運用上使われず、実支払額の定義が単純になる。

オーナーの明示決定により、支払履歴（支払の消し込み記録）の概念を過去データを含めて削除する。決定 D-23（10年保存）は検討したうえで、削除が明示決定された。

## 追記: 入金（Receipts）— 入金管理をステータスだけで管理する

支払側の残金・支払履歴の廃止（上記 Removals）と同じ考え方を、売上管理表（案件の入金）にも適用する。オーナーの明示決定による。

### 決定内容

- **入金額は手入力しない**: 入金の消し込み履歴、残金・残額、入金額の手入力を廃止した。案件の入金額は入金ステータスから導出する（`src/lib/actual-received.ts`）: 入金済（案件ステータス 全額入金済み）→ 案件の契約金額（`projects.amount`）、それ以外 → 0。
- **入金ステータスは 未入金 / 入金済 の2つだけ**: 一部入金を全面廃止した（案件ステータス 一部入金済み も廃止）。案件ステータスは 未対応、提案中、見積確認中（表示は 見積書提出済み）、受注（表示は 契約済み）、請求書発行済み、全額入金済み、失注、オーダー移行。入金ステータスの変更は `projects.updateReceiptStatus`（未入金 → 請求書発行済み、入金済 → 全額入金済み）。確定（lock）済みでも変更でき、誤操作を戻せるよう 入金済 → 未入金 も許可する（従来の前進のみ制限は廃止）。
- **入金日は導出する**: `projects.paid_at`（timestamp、NULL許容）を新設した。ステータスが 全額入金済み になったとき `updateReceiptStatus` が設定し（既に全額入金済みなら既存値を保つ）、全額入金済み から外れたらクリアする（`src/lib/paid-at.ts`）。月の判定は JST（`jstYearMonth`）。引渡月変更の複製は `paid_at` を引き継ぐ。
- **集計**: 入金実績 = 全額入金済み の案件の契約金額を `paid_at` の月で集計。入金予定 = 未入金の案件の契約金額を請求書の入金期日（`invoices.due_date`）の月で集計（`src/lib/receipt-summary.ts`）。
- **削除したもの**: `receipts` テーブル、`receipts.list/create/update/delete`、入金明細・消し込み履歴・入金登録の画面、入金額累計・当月入金額・前月までの入金額・完成工事未収入金・未成工事受入金の列、入金CSV（`/api/export/receipts`）、`receipts` の履歴（監査ログ）。売上CSV（`/api/export/sales`）は入金額（導出）と入金日の列に変更した。
- **残すもの**: 案件外入金（`misc_receipts`）は金額入力を残す（工事外支払と同じ）。ステータスのみ 未入金 / 入金済 に限定し、未知の値・一部入金 は 未入金 として扱う（`normalizeReceiptStatus`）。請求書の未請求残金（分割請求、`invoices.is_split`）は別概念として残す。監査ログの仕組みは残す。
- **UI**: 支払い予定表と同じ。入金済の行は行ごとグレー（`receiptRowClass`）、未入金は黄バッジ、入金済はグレーバッジ、ステータス文言は常に表示する。

### Removals（入金）

オーナーの明示決定により、入金の消し込み履歴を過去データを含めて削除する。決定 D-23（10年保存）は検討したうえで、削除が明示決定された。

- 削除対象: `receipts` テーブル、監査ログ `table_name = 'receipts'` の行（『入金登録』履歴）。
- データ更新: 案件ステータス 一部入金済み → 請求書発行済み（`version` を進める）、`misc_receipts.status` の 一部入金 → 未入金。案件・受注・請求書・案件外入金の行は削除しない。
- 追加: `projects.paid_at`（STEP 1。既存の全額入金済み案件へは `receipts` の最大入金日 → 請求書の入金期日 → 実行時刻の順でバックフィル）。

## 追記: 売上管理表への改称と案件外タブの廃止（Receipts screen renamed and 案件外 tab removed）

## 追記: 支払IDの月形式と定期支払いへの事前採番（Payment ID month format & recurring IDs）

オーナーの指示による。上記の「支払No（案件外）」の形式を置き換える。

### 決定内容

- **形式**: 工事外の支払IDを `WW{期2桁}-{月2桁}-{NNN}`（例: `WW07-10-001`）にする。月は支払月（支払日の年月。定期支払いは対象月 `period`）、期はその月が属する会計期（`fiscalPeriodOfMonth` と `fiscalPeriodLabel`）。支払日が無い・不正な支払は作成月（JST）を使う。
- **連番**: 同じ期・月の接頭辞の末尾連番の最大値+1。接頭辞キーの `pg_advisory_xact_lock` を取った作成トランザクション内で採番する。一度付けた番号は編集で振り直さない（凍結）。旧形式（`-000-`）の番号は新接頭辞に一致しないため無視され、月ごとに 001 から始まる。
- **定期支払いも支払前から採番**: `recurringPayments.ensureMonth({ month })` が、その月に有効で「支払なし」でなく、行の無い定義ごとに `misc_payments` の未払い行を作り、支払IDを付与する（月ロック付きの1トランザクション、`(recurring_id, period)` の unique index に対し ON CONFLICT DO NOTHING、冪等。作成があったときだけ監査ログ）。工事外タブが月の表示時に呼ぶ。
- **整合ルール**:
  - 支払なし（skipMonth）: 未払いの具体化行は削除して支払なしを記録する。支払済みの月は拒否する。
  - 支払なしを戻す（unskipMonth）: 支払なしを外し、その月の未払い行を新しい支払IDで作り直す（同一トランザクション）。
  - 定義の編集: 当月以降の未払い行は、新しい予定でも対象月なら項目を更新（支払IDは保持）、対象月でなくなったら削除する。支払済みと過去月は触らない。
  - 定義の削除: 当月以降の未払い行を削除する。支払済みは保存義務のため残す（月次ビューでは定義削除済みとして表示）。
  - 支払済み → 未払い（markPlanned）は行を残す。`payments.misc.delete` は支払ID付き・定期由来の行を引き続き削除できない。
- **注意**: 未払い行の削除により、その月の最大連番の番号は再利用され得る（未払い行は一度も支払われていないため許容）。

### 適用手順（厳守）

保守担当が次の順で実施する。エージェントはDBへ書き込まない。

1. 新アプリをデプロイする。
2. バックアップを取る（Supabase のスナップショット等）。
3. `psql "$DATABASE_URL" -f scripts/sql/2026-10-misc-payment-no-month.sql` を流す（破壊的・単一トランザクション・冪等。旧形式の番号を支払月の接頭辞で振り直し、前後対応表を表示する）。

デプロイ後〜SQL実行前に作られた行は新形式で採番済み。旧形式の行はそのまま残る（新接頭辞とは一致しないため、新しい番号は月ごとに 001 から始まる）。SQL はその状態を整合させ、既に発行済みの新形式の最大連番の次から旧行へ振る。
