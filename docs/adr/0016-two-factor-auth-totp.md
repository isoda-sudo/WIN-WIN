# ADR-0016: ログインに2段階認証（認証アプリ＋リカバリーコード）を導入

## メタ情報

- **ステータス**: 提案中(Proposed)
- **日付**: 2026-10-21（2026-10-22 改訂: スマホ2台まで・本人による無効化の廃止）
- **決定者**: Claude Code（承認: パニ / H Paniagua L A。本番適用前に梅田さんが最終確認）

## コンテキスト（背景と課題）

ログインはメールアドレス＋パスワードのみで、パスワードが漏れると取引先の担当者情報・口座情報・金額を含む全データが見られる。09-16 定例で「パスワード以外の認証を追加する。認証アプリ（30秒ごとの6桁コード）＋端末の生体認証を第一候補として検証する」と決まった（D-24）。09-24 に PoC（`poc/2fa-totp-passkey` ブランチ、`/poc-2fa`）を作成し、09-25 定例で方式比較を提示した。ただし必須にするロール・スマホ紛失時の復旧手順などの方針（O-07）は未決のまま。

制約:

- DB は旧 Express アプリと共有しており、既存テーブルの変更は避けたい（Hard Rule 1）。新規テーブルの追加のみなら旧アプリは無視する
- セッションは httpOnly クッキーの JWT（7日）で、`token_version` で失効させる既存の仕組みがある
- Vercel のサーバーレス環境では、メモリ上のカウンタはインスタンスごとにばらばらになる
- 本番ドメインがまだ確定していない（パスキーは登録したドメインに固定される）

## 検討した選択肢

### 選択肢A: 認証アプリ（TOTP）＋リカバリーコード

- 長所: 端末や PC の機種に依存しない。オフラインの現場でも使える。Google Authenticator のプライバシースクリーン（Face ID でアプリを開く）で「生体認証」の要望にコードなしで応えられる。ドメインに依存しない
- 短所: フィッシングには弱い（コードを偽サイトに入力させられる）

### 選択肢B: パスキー（WebAuthn、端末の生体認証）

- 長所: フィッシングに強い。サーバー側で生体認証まで確認できる
- 短所: 登録した本番ドメインに固定されるため、ドメイン確定前に登録すると全員分が無効になる。端末・ブラウザによって挙動が異なる

### 選択肢C: メールでのワンタイムコード

- 長所: アプリのインストールが不要
- 短所: メールアカウントを乗っ取られると突破される。SMTP の到達遅延がログインに直結する

### 選択肢D: Google アカウント連携（SSO）

- 長所: パスワード管理が不要
- 短所: 09-11 に提案したが選ばれなかった（D-24）

## 決定内容

選択肢Aを採用する。パスワード確認後、2段階認証を設定済みのユーザーには認証アプリの6桁コード（またはリカバリーコード）を求め、確認できてからセッションを発行する。パスキー（選択肢B）は本番ドメイン確定後に追加できる構造にしておき、今回は入れない。

構成:

- **テーブル（新規のみ）**: `user_mfa`（ユーザー単位の有効化日時・失敗回数・ロック期限）、`user_mfa_devices`（スマホごとの名前・暗号化した TOTP シークレット・最後に使ったステップ・登録日時・最終使用日時。登録途中は1人1行まで）、`user_recovery_codes`（HMAC ハッシュ、使用日時）。DDL は `scripts/sql/2026-10-user-mfa.sql`（2FA 用テーブルのみ・冪等。10-21 版を適用済みなら、設定済みの鍵を `user_mfa_devices` に「スマホ1」として移してから `user_mfa` の旧列を除去）
- **スマホは1人2台まで**: 機種変更・紛失時は、ログイン後（リカバリーコードでも可）に「スマホを追加」で新しいスマホを登録し、古いスマホを削除する。ログイン時はどちらのスマホのコードでも通る。リカバリーコードは最初のスマホを設定したときに発行し、スマホの追加・削除では変わらない
- **追加の確認**: ログインから15分以内のセッション＋新しいスマホのコードで追加できる（JWT の `iat`）。セキュリティ設定からの初回設定も同じく15分以内に限る（ログイン時・招待受諾時の初回設定は、パスワード確認直後の保留中トークンで行うので対象外）。既存スマホのコードは求めない（スマホを紛失した人が追加できなくなるため）。リカバリーコードでログインした直後は必ず15分以内なので、紛失時の手順はそのまま使える。追加は名前付きで監査に残す
- **削除の確認**: もう1台のスマホのコードで確認する（削除するスマホ自身のコードは不可）。最後の1台は削除できない。追加・削除はユーザーの行を `FOR UPDATE` でロックして行い、同時操作でも2台を超えず、0台にならない
- **無効化は管理者のみ**: 一度設定したら、本人は2段階認証をやめられない（常に1台以上のスマホが登録された状態）。やめる・全台紛失した場合は管理者リセット（全スマホとリカバリーコードを削除）のみ
- **トークン**: JWT に `aud` を付け、セッション（`session`、7日）と「パスワードは確認済み・コード未確認」の保留中トークン（`mfa_pending`、5分、クッキー `mfa_pending`）を分ける。保留中トークンはセッションとして通らない
- **有効化の切り替え**: 環境変数 `MFA_ENCRYPTION_KEY`（32バイト hex）が未設定の間は2段階認証を一切使わず、従来どおりのログインになる
- **方針（O-07 が決まるまでの暫定）**: 任意設定（本人が「セキュリティ設定」で有効化）。`MFA_REQUIRED_ROLES`（例 `admin,accounting`）に書いたロールは、未設定ならログイン時・招待受諾時に設定画面へ送り、設定するまでセッションを発行しない
- **権限（Hard Rule 2）**: 本人の設定（有効化・スマホの追加と最後の1台以外の削除・リカバリーコード再発行）は全ロールが自分のアカウントについて使える `protectedProcedure`。2段階認証の無効化（他人のリセット）は `adminProcedure` のみ（パニの回答、2026-10-21・2026-10-22・2026-10-23）
- **安全策**: コード誤り5回で15分ロック（DB の `failed_attempts` / `locked_until`）。使用済みコードの再利用は条件付き UPDATE で防ぐ。シークレットは AES-256-GCM（ユーザー ID を AAD）で暗号化。リカバリーコードは鍵由来のペッパー付き HMAC-SHA256。再発行は登録しているスマホのコードで再確認する
- **監査（Hard Rule 3）**: 有効化・スマホの追加と削除（名前付き）・再発行・リカバリーコード使用・コード誤り・ロック・管理者リセットを `logAudit`（`table_name = users`）に記録する。シークレット・QR・コードは記録しない

## 決定の理由

D-24 の第一候補であり、09-25 の比較でも推奨した方式。旧アプリと共有の DB に対して既存テーブルを変えずに済み、環境変数で段階的に有効化できるため、本番適用の順序（デプロイ → SQL 適用 → 鍵の設定）を安全に組める。O-07 が未決でも、必須ロールを環境変数で切り替えられるので、決定後にコード変更なしで方針を反映できる。パスキーはドメイン未確定という外部要因で今は入れられないが、PoC のコア部分（`webauthn.ts`）はそのまま後から追加できる。

## 影響

### ポジティブ

- パスワードが漏れても、本人のスマホが無ければ新アプリにはログインできない
- `MFA_ENCRYPTION_KEY` を設定するまでは挙動が変わらないため、コードを先にデプロイできる
- ログイン試行制限が失敗のみを数えるようになり、同じ IP の事務所で成功ログインが上限を消費しなくなる

### ネガティブ

- JWT に `aud` を付けたため、デプロイ時点の既存セッションはすべて無効になり、全員が一度ログインし直す
- 旧 Express アプリは同じユーザーでパスワードのみのログインができるため、旧アプリを止める（または IP 制限する）までは2段階認証を迂回できる
- セッションは7日のままなので、2段階認証を求めるのは週1回程度
- `MFA_ENCRYPTION_KEY` を失う・変えると、全員の2段階認証が使えなくなる（管理者リセット → 再設定が必要）
- 2台とも紛失した場合は、リカバリーコードでログインしても追加（上限）も削除（もう1台のコードが必要）もできないため、管理者リセットが必要
- 本人が2段階認証をやめられないため、不要になった場合も管理者への依頼が必要
- ログインから15分以内のセッションを盗まれた場合（またはパスワードとコードの両方を盗まれた場合）は、攻撃者が自分のスマホを追加（未設定の人なら初回設定）し、そのスマホのコードで本人のスマホ削除・リカバリーコード再発行までできる。本人は管理者リセットで復旧する。15分を過ぎた古いセッションでは追加できない
- 認証アプリに表示される発行者名（`株式会社WIN WIN`、`src/server/pdf/company.ts`）は各スマホに登録時点の名前で残る
