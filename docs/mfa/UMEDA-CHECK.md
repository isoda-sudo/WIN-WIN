## 0. 何が入っているか（3行で）

1. パスワードの後に、スマホの認証アプリ（Google Authenticator など）の6桁コード、またはリカバリーコードを入力するログイン
2. 本人用の「セキュリティ設定」画面（右上の盾アイコン）：有効化・スマホの追加と削除（1人2台まで、最後の1台は削除不可）・リカバリーコード再発行。本人は2段階認証をやめられない（やめる・全台紛失は管理者リセット）。セキュリティ設定からの初回設定とスマホの追加は、ログインから15分以内に限る
3. 管理者用：アカウント発行画面に「2段階認証」列と「リセット」ボタン（スマホ紛失時）

パスキー（ブラウザの生体認証）は**入れていません**。本番ドメインが決まる前に登録すると、ドメイン変更時に全員分が使えなくなるためです。生体認証は、Google Authenticator のプライバシースクリーン（アプリを Face ID で開く）で対応します（09-16 定例の合意）。

## 8. 確認できていないこと

- スマホ追加・削除の同時操作（2台を超えない・0台にならない）を守る DB ロック（`store.ts` の `FOR UPDATE`）は、実 DB で同時に2件削除して1台残ることを手動で確認しただけで、自動テストはない（このブランチには DB を使うテストの仕組みが無いため）

- 実機のスマホ（Google Authenticator）での読み取り（QR と手入力キーは仕様どおり生成）
- Vercel の本番環境（複数インスタンス・Supabase の接続プール経由）での動作
- ログイン試行制限（IP ごと、10回／15分）はメモリ上のため、インスタンス間で共有されない（既存の課題のまま。2段階認証のコード誤りは DB でアカウントごとに数えるので影響なし）
- 送信元 IP は `x-forwarded-for` の先頭を使っている（既存のログインと同じ）
- コード誤りの回数は、正しいコードで入るまで（またはロック明け）減りません（日をまたいでも累積）
- 設定途中（QR を出したが未完了）の QR は10分間だけ同じものを再表示し、それ以降は新しい QR になります
