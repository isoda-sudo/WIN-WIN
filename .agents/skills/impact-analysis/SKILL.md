# インパクト分析

## Overview

新機能や変更が既存のコードベース・機能に与える影響を体系的に調査し、リスクと対応策をレポートにまとめる。
コードベースの自動分析と対話を組み合わせ、見落としがちな影響を洗い出す。

## The Process

### Phase 1: 変更内容の明確化

まず何を変更・追加するのかを特定する:

1. 関連ドキュメントを確認:
   - `docs/requirements/` のPRD
   - `docs/stories/` のユーザーストーリー
   - `docs/screens/` の画面仕様
2. ユーザーに質問: 「何を変更・追加しますか？（概要を教えてください）」
3. 変更の種類を分類:
   - **新機能追加**: 新しい画面・API・コンポーネントの追加
   - **既存機能の変更**: 振る舞いの変更、UI変更
   - **リファクタリング**: 構造変更、技術的負債の解消
   - **依存関係の更新**: パッケージ更新、外部API変更
   - **削除**: 機能・コードの除去

### Phase 2: 影響範囲の調査

コードベースを自動分析して影響範囲を特定する。依存先を追跡せずに変更対象のファイルだけ見ると、思わぬ箇所が壊れるリスクがある。上流（このコードが依存しているもの）と下流（このコードに依存しているもの）の両方向で追跡する。

**調査対象（変更の種類に応じて選択）:**

| 調査領域 | 調査方法 | 対象ディレクトリ |
|---------|---------|-----------------|
| tRPCルーター | import/export追跡、プロシージャ参照 | `src/server/api/routers/` |
| ページ | ルーティング、データフェッチ | `src/app/**/page.tsx` |
| コンポーネント | props依存、コンポーネントツリー | `src/components/`, `src/app/_components/` |
| ユーティリティ | 関数参照、型定義 | `src/lib/` |
| スタイル | デザイントークン、CSS変数 | `src/styles/globals.css` |
| テスト | テストカバレッジ、テストの依存 | `__tests__/`, `e2e/` |
| 設定 | ビルド設定、環境変数 | `next.config.js`, `.env*` |

**調査手順:**
1. 変更対象のファイル/シンボルを特定
2. import/exportの依存グラフを追跡（上流・下流の両方向）
3. 影響を受けるファイルを一覧化
4. 各ファイルの影響内容を簡潔にまとめる

複数の独立した調査領域がある場合は、`dispatching-parallel-agents` スキルで並行調査する。

### Phase 3: リスク評価

影響を受ける各箇所について、リスクを評価する。

**評価基準:**

| 基準 | High | Medium | Low |
|------|------|--------|-----|
| **影響度** | 主要機能が壊れる | 一部機能に影響 | 表示・見た目のみ |
| **複雑さ** | 大規模な変更が必要 | 中程度の変更 | 軽微な変更 |
| **テスト状況** | テストなし | 部分的にカバー | 十分にカバー |
| **型安全性** | 型定義の破壊的変更 | 型の追加・修正 | 型への影響なし |

テストカバレッジの確認は特に重要。テストのない箇所の変更は、意図しない振る舞い変更を検出できないため、リスクが跳ね上がる。

**各影響箇所で評価する項目:**
- 影響度（High/Medium/Low）
- 変更の複雑さ
- 既存テストカバレッジ
- 型安全性への影響
- ユーザー体験への影響

### Phase 4: 対応策の提案

リスクを列挙するだけでは判断材料にならない。各リスクに対して具体的な対応策を提案する。

**対応策のカテゴリ:**
- **予防策**: 変更前に実施すること（テスト追加、型定義の整理）
- **軽減策**: 影響を最小限にする方法（段階的リリース、フィーチャーフラグ）
- **検証策**: 変更後に確認すること（回帰テスト、手動テスト項目）

**推奨実装順序の提案:**
リスクの低い箇所から着手し、影響が大きい箇所は十分なテストを書いてから変更する。この順序を示すことで、PMが「どこから手をつけるべきか」を判断できる。

**破壊的変更の特定:**
- APIの型シグネチャ変更
- コンポーネントのprops変更
- データベーススキーマの変更
- URLパスの変更

### Phase 5: レポート出力

分析結果をレポートとして出力する。

**影響マップの図（オプション）:**
影響範囲が広い場合（影響ファイル10件以上）や、依存関係が複雑な場合は、`drawio` スキルを使って影響マップを視覚化できる。ユーザーに必要か確認してから作成する。
- 変更起点から影響が波及するモジュールの関係図
- 影響度に応じた色分け（High: 赤、Medium: 黄、Low: 緑）
- 保存先: `docs/analysis/` に `.drawio` または `.drawio.png` で配置

**出力テンプレート:**

```markdown
# インパクト分析レポート: {変更名}

## 変更概要
{変更内容の要約}

## 影響マップ
{Mermaid graph または draw.ioファイルへの参照}

## 影響を受けるファイル

| ファイル | 影響度 | 影響内容 | 対応策 |
|---------|--------|---------|--------|
| {パス} | High/Medium/Low | {内容} | {対策} |

## リスク一覧

| リスク | 深刻度 | 発生確率 | 対応策 |
|--------|--------|---------|--------|
| {リスク} | High/Medium/Low | High/Medium/Low | {対策} |

## テスト影響

### 影響を受ける既存テスト
- {テストファイル}: {影響内容}

### 追加が必要なテスト
- {テスト内容}: {理由}

## 推奨実装順序
1. {ステップ1}（理由: {理由}）
2. {ステップ2}（理由: {理由}）
3. ...

## まとめ
- 影響ファイル数: {N}件（High: {n}, Medium: {n}, Low: {n}）
- 主要リスク: {最も注意すべきリスクの要約}
- 推奨アプローチ: {一言でのアプローチ要約}
```

**保存先:** `docs/analysis/YYYY-MM-DD-<change-name>-impact.md`

**次のステップを提案:**
- 「実装計画を立てますか？」→ `writing-plans` スキル
- 「ストーリーに分解しますか？」→ `user-story-breakdown` スキル
- 「コードベースをもっと深く調べますか？」→ `analyze-codebase` スキル

## Key Principles

- **両方向に追跡** — 変更元からの下流だけでなく、上流の依存も確認する。上流が変わっていた場合、自分の変更の前提が崩れている可能性がある
- **テスト状況を確認する** — テストがない箇所を変更すると、壊れたことに気づけない。テストカバレッジの有無がリスク評価の最大の判断材料になる
- **型の波及を見逃さない** — TypeScriptの型変更は、直接の依存先だけでなく、re-exportや型推論を通じて広範囲に影響する。`tsc --noEmit` で全体の型整合性を確認するのが最も確実
- **推奨順序を提示する** — リスクの低い箇所から着手する計画を立てることで、PMが開発の進め方を判断しやすくなる
- **過不足なく報告** — 影響がない箇所をレポートに含めるとノイズになり、本当に重要なリスクが埋もれる

## Common Mistakes

- 変更対象のファイルだけ見て、依存先を追跡しない
- テストカバレッジの確認を省略する
- 型の変更による波及を見落とす
- 対応策なしでリスクだけ列挙する
- 実装順序の提案を忘れる
