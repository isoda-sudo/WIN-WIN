# 要件定義・PRD作成

## Overview

ヒアリングベースの対話を通じて、PRD（プロダクト要件定義書）を段階的に作成する。
一度に1つの質問を投げかけ、回答を積み重ねることで、曖昧なアイデアを構造化された要件定義書に変換する。

## The Process

### Phase 1: コンテキスト理解

まずプロジェクトの現状を把握する:
- CLAUDE.md、既存のドキュメント（`docs/`）、最近のコミットを確認
- `docs/requirements/` に既存のPRDがあれば目を通す

次に、以下の質問を **1つずつ** 投げかける:
1. 「何を作りますか？（1-2文で）」
2. 「誰が使いますか？（ターゲットユーザー）」
3. 「なぜ必要ですか？（現状の課題や背景）」
4. 「成功とは何ですか？（達成したいゴール）」

選択式で回答しやすくできる場合は、選択肢を提示する。回答が曖昧なら深掘りする。

### Phase 2: スコープ定義

ユーザーの回答をもとに、スコープ候補を提示する:

**In-Scope（対象範囲）の候補を提示:**
- 回答から推測される機能を箇条書きで提示
- ユーザーに追加・削除を確認

**Out-of-Scope（対象外）の候補を提示:**
- 将来的に検討するが今回は含めないもの
- 明確に対象外とするもの

スコープの境界が曖昧な場合は、具体的な選択式の質問で絞り込む:
- 「〇〇の機能は含めますか？」→ はい / いいえ / 将来検討

### Phase 3: 機能要件の洗い出し

In-Scopeの各機能について、1つずつ深掘りする:

各機能につき200-300語程度で以下を整理し、セクションごとに確認を取る:
- **期待される動作**: ユーザーが何をすると何が起きるか
- **入力と出力**: どんなデータを受け取り、何を返すか
- **エッジケース**: 異常系やバウンダリケース
- **優先度**: Must / Should / Could / Won't（MoSCoW法）

全機能の洗い出しが終わるまで、1機能ずつ繰り返す。

### Phase 4: 非機能要件・制約

プロジェクトの技術スタックを踏まえたデフォルト値を提示しつつ、確認する:

- **パフォーマンス**: レスポンス時間、同時接続数（デフォルト提案あり）
- **セキュリティ**: 認証・認可、データ保護
- **アクセシビリティ**: WCAG準拠レベル
- **対応ブラウザ・デバイス**: モバイル対応の範囲
- **技術的制約**: 使用技術の制限、外部サービス連携

「特にこだわりがなければデフォルトで進めますか？」と確認し、不要な深掘りを避ける。

### Phase 5: PRD生成・レビュー

`references/prd-template.md` のテンプレートに沿ってPRDを生成する。

**出力手順:**
1. テンプレートを読み込む: `references/prd-template.md`
2. ヒアリング内容を埋め込んでPRDを生成
3. セクションごとに提示してレビューを受ける（200-300語ずつ）
4. 修正があれば反映
5. 最終版を `docs/requirements/YYYY-MM-DD-<feature-name>-prd.md` に保存

**図の出力（オプション）:**
システム構成図やデータフロー図があると全体像が伝わりやすい場合は、`drawio` スキルを使って `.drawio` ファイルとして出力できる。ユーザーに必要か確認してから作成する。
- システム構成図: 外部サービスとの連携関係
- データフロー図: データの流れと変換
- 保存先: `docs/requirements/` に `.drawio` または `.drawio.png` で配置

**次のステップを提案:**
- 「ユーザーストーリーに分解しますか？」→ `user-story-breakdown` スキル
- 「画面仕様を定義しますか？」→ `screen-specification` スキル
- 「アイデアをもっと掘り下げますか？」→ `brainstorming` スキル

## Key Principles

- **1回に1つの質問** — 複数の質問を同時に投げると、回答がぼやけたり、PMが考えるべきポイントを見落としやすくなる
- **選択式を優先** — 自由回答よりも選択肢がある方が認識のズレを防げる。ただし自由に語ってもらうべき場面（背景や課題感）では開放型の質問にする
- **200-300語ずつ提示** — 長い文書を一気に見せると見落としが増える。セクション単位で確認を取ることで、各部分の品質を担保する
- **プロジェクト文脈を活用** — 技術スタックや既存コードから推測できることはデフォルト提案として示す。PMの負荷を減らしつつ、認識齟齬を早期に発見できる
- **YAGNIの徹底** — 「あったら便利」な機能を盛り込むとスコープが膨らみ、実装の遅延やコスト超過を招く。In-ScopeとOut-of-Scopeの明確な線引きが重要
- **柔軟に戻る** — ヒアリングが進む中で前提が変わることはよくある。前のフェーズに戻って修正することをためらわない

## Common Mistakes

- ヒアリングを省略していきなりPRDを書き始める
- 全質問を一度に投げて圧倒する
- 技術的な実装詳細を要件定義に含めすぎる
- Out-of-Scopeを定義し忘れてスコープクリープを招く
- 非機能要件を後回しにしすぎる
