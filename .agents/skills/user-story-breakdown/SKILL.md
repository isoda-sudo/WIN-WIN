# ユーザーストーリー分解

## Overview

エピック（大きな機能単位）をユーザーストーリーとタスクに段階的に分解する。
INVEST原則による品質チェックを行い、エンジニアが実装に取りかかれる粒度まで落とし込む。

## The Process

### Phase 1: 入力の確認

まず分解対象を特定する:

1. `docs/requirements/` にPRDが存在するか確認
   - あれば読み込んで内容を要約して提示: 「このPRDをもとにストーリー分解しますか？」
   - なければ次へ
2. PRDがない場合、ユーザーに質問:
   - 「どんな機能をストーリーに分解しますか？（概要を教えてください）」
   - 必要なら `requirements-definition` スキルの利用を提案
3. エピックレベルの名前と概要を確定する

### Phase 2: ユーザーストーリー分解

エピック内の機能領域ごとに、ストーリーを生成する。

**手順:**
1. 「この機能の主なユーザーは誰ですか？」と質問（選択式で提示）
2. ユーザー種別ごとにストーリーを生成:

**ストーリー形式:**
```
[ユーザー]として、[目的]のために、[機能]をしたい
```

3. 3-5個のストーリーをまとめて提示し、確認を取る
4. 各ストーリーに受け入れ基準を付与（Given/When/Then形式）:

**受け入れ基準の形式:**
```
Given: [前提条件]
When: [操作・アクション]
Then: [期待される結果]
```

5. ユーザーの確認後、次の機能領域へ進む

**ストーリーの粒度の目安:**
- 1-3日で実装完了できるサイズ
- 1つのストーリーは1つの価値提供に集中
- 技術タスク（リファクタリング等）はストーリーとは分けて管理

### Phase 3: INVEST品質チェック

全ストーリーが出揃ったら、`references/invest-checklist.md` を参照して品質チェックを行う。

品質チェックを行う理由: INVESTに沿っていないストーリーは、実装着手後に「思ったより大きかった」「他のストーリーと依存していた」といった手戻りを生む。ここで検出しておくと、スプリント計画の精度が大幅に上がる。

**チェック手順:**
1. 各ストーリーをINVEST基準で評価
2. 結果を表形式で提示:

| ストーリー | I | N | V | E | S | T | 問題点 |
|-----------|---|---|---|---|---|---|--------|
| {ストーリー名} | OK/NG | OK/NG | ... | ... | ... | ... | {具体的な問題} |

3. NG項目があるストーリーについて、修正案を提示
4. ユーザーの承認後、修正を反映

### Phase 4: タスク分解・出力

各ストーリーを実装タスクに分解する。

**TDD対応のタスク分解:**
このプロジェクトではt-wada式TDDを採用しているため、各ストーリーにつきテスト→実装の順でタスクをペアにする:
1. テストタスク: 「{ストーリー名}のテストを作成」
2. 実装タスク: 「{ストーリー名}を実装」

**ストーリーマップ図（オプション）:**
ストーリー数が多い場合（10個以上）や、ストーリー間の関係を俯瞰したい場合は、`drawio` スキルを使ってストーリーマップを図示できる。ユーザーに必要か確認してから作成する。
- 横軸: ユーザーのアクティビティ（大きな流れ）
- 縦軸: 優先度（上が高い）
- 保存先: `docs/stories/` に `.drawio` または `.drawio.png` で配置

**出力モードを選択:**

ユーザーに選択してもらう:
- **Markdownファイル**: `docs/stories/YYYY-MM-DD-<epic-name>-stories.md` に保存
- **GitHub Issues**: `create-github-issue` スキルを使ってEpic Issue + Story Issuesを作成（ラベル・マイルストーン付き）
- **両方**: Markdownに保存しつつ、GitHub Issuesも作成

**Markdown出力のフォーマット:**
```markdown
# エピック: {エピック名}

## 概要
{エピックの概要}

## ユーザーストーリー一覧

### US-001: {ストーリー名}
**ストーリー:** [ユーザー]として、[目的]のために、[機能]をしたい
**優先度:** Must / Should / Could
**受け入れ基準:**
- Given: ... When: ... Then: ...

**タスク:**
- [ ] テスト作成: {テスト内容}
- [ ] 実装: {実装内容}
```

**次のステップを提案:**
- 「画面仕様を定義しますか？」→ `screen-specification` スキル
- 「影響分析を行いますか？」→ `impact-analysis` スキル
- 「実装計画を立てますか？」→ `writing-plans` スキル

## Key Principles

- **1回に1つの質問** — 質問を重ねると、PMが各ストーリーの意図を十分に吟味できなくなる
- **ストーリーはユーザー価値で切る** — 「DBスキーマを変更する」のように技術レイヤーで切ると、ビジネス価値が見えなくなり、優先度判断ができなくなる。「ユーザーが〇〇できる」という形にすることで、ステークホルダーとの会話にも使える
- **受け入れ基準は必須** — 基準のないストーリーは「完了」の定義が曖昧になり、PMとエンジニアの認識がズレる原因になる
- **INVESTチェックを省略しない** — スプリント開始後に「このストーリー、思ったより大きい」となるのを防ぐためのセーフティネット
- **TDDを前提にタスク分解** — テストタスクと実装タスクをペアにすることで、プロジェクトのTDD方針と自然に整合する

## Common Mistakes

- ストーリーを技術タスク（「DBスキーマを変更する」）として書いてしまう
- 1つのストーリーに複数の価値提供を詰め込む
- 受け入れ基準が曖昧（「正しく動作する」等）
- INVEST品質チェックを省略する
- ストーリー間の依存関係を無視する
